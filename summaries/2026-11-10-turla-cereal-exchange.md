# Technical Analysis Report: Turla "Cereal" Modular Exchange Server Backdoor (2026-11-10)

Prepared by: Actioner
Classification: TLP:CLEAR
Date: 2026-11-10
Version: 2 (REVISED)

## Executive Summary

ESET Research has disclosed a previously undocumented, modular espionage toolset dubbed "Cereal," attributed with high confidence to the Russia-aligned APT group Turla (also known as Snake, tracked as MITRE G0010, linked to Russia's FSB). The toolset was discovered actively targeting Microsoft Exchange servers at governmental organizations in Kazakhstan (since November 28, 2025) and Romania (since December 23, 2025). In the Romanian case, operators configured the email harvesting component to intercept communications involving NATO and EU institutional addresses.

The Cereal toolset is architecturally notable for several reasons: (1) it uses **no external C2 infrastructure** -- the compromised Exchange server itself becomes the command-and-control hub; (2) nearly all components are .NET assemblies that **never touch disk**, being decrypted, deserialized, and executed entirely in memory; (3) the email collection module (CerealBox) hijacks Exchange transport agents **in memory** without registering a new agent, a novel technique requiring deep understanding of Exchange internals; and (4) the toolset abuses several low-level .NET mechanisms including unmanaged entry points, VTable Fixups, and native image cache poisoning.

The viability gate passes: ESET provides 18 file hashes (SHA-1), specific listener URI paths, file system paths, DLL names, process injection targets, MITRE ATT&CK mappings (30+ technique IDs), and detailed behavioral signatures sufficient for production-quality detection rules.

## Background

### Turla Group Profile

Turla is an advanced persistent threat group active since at least 2004, possibly extending back to the late 1990s. It is attributed to Russia's Federal Security Service (FSB) and has compromised victims in over 50 countries, primarily targeting government and diplomatic entities across Europe, Central Asia, and the Middle East. Notable prior compromises include the US Department of Defense (2008) and Swiss defense firm RUAG (2014). ESET has previously documented Turla's arsenal including LightNeuron (2019), ComRAT v4 (2020), and Crutch (2020).

### Campaign Context

- **Kazakhstan victim**: Governmental organization compromised since at least November 28, 2025. Operator activity surged on January 15, 2026 (immediately following Russian Old New Year on January 14), suggesting operators resuming after holidays.
- **Romania victim**: Governmental organization compromised since at least December 23, 2025, with increased activity from January 20, 2026. CerealBox was configured to collect emails involving `nato[.]int` and `europa[.]eu` addresses, consistent with Russian intelligence priorities regarding NATO and EU affairs.
- **Initial access**: Unknown. Given the internet-facing Exchange servers, ESET assesses exploitation of an Exchange vulnerability as a plausible vector.

## Technical Analysis

### Toolset Architecture

The Cereal toolset comprises eight interconnected components, most of which operate entirely in memory. The name "Cereal" derives from the heavy use of .NET serialization across all components.

```
Operator --> CerealNeuron (passive listener on Exchange)
                |
                v
            CerealRunner (command container/executor)
                |
                +---> CerealSprinter (component loader)
                |         |
                |         +---> CerealNeuron (backdoor)
                |         +---> CerealHermit (offline backdoor)
                |         +---> CerealBox (email harvester)
                |
                +---> CerealIron (process injector)
                |         |
                |         +---> Bootstrapper DLLs (x86/x64)
                |
                +---> CerealMoth (assembly loader)
                |
                +---> CerealLoader (disk-based loader)
```

### Stage 1: Persistence -- CerealLoader

CerealLoader is the **only component written to disk** as a recognizable .NET file. It reads an encrypted file from disk, decrypts it (using RC4 or XOR with a 255-byte key), loads the resulting .NET assembly, and invokes one of its methods.

**Key persistence mechanisms:**

1. **DLL Search Order Hijacking** (T1574.001):
   - Placed as `ncobjapi.dll` in `C:\Windows\System32\wbem\` -- loaded by WMI Provider Host (`WmiPrvSE.exe`)
   - Placed as `wbemcomn.dll` in `C:\Windows\System32\wbem\` -- hijacks the legitimate `wbemcomn.dll` from `C:\Windows\System32\`, forwarding all legitimate exports

2. **.NET Native Image Cache Poisoning**:
   - Files placed in `C:\Windows\assembly\NativeImages_v4.0.30319_64\` with names mimicking legitimate Exchange native images (e.g., `Microsoft.Exchange.Search.Mdb.ni.dll`)
   - Not generated by `ngen.exe` but manually copied with elevated privileges
   - One variant checks if the parent process is `Microsoft.Exchange.Search.Service` before executing

**Anti-analysis technique -- Mixed-Mode Execution:**
CerealLoader uses the `COMIMAGE_FLAGS_NATIVE_ENTRYPOINT` flag (value `0x10`) in the .NET CLI header to execute native code before any managed code runs. The actual malicious logic resides in a method (`RaiseOnRoutedMessage`) that is never referenced in .NET code -- it is invoked through **VTable Fixups** that create a bridge from native code to managed code. Standard .NET decompilers (e.g., dnSpy) miss this execution path entirely.

All components are obfuscated with **ConfuserEx** using control flow obfuscation and string encryption, with custom symbol renaming that mimics legitimate Microsoft component names.

### Stage 2: Command Delivery -- CerealRunner & CerealSprinter

**CerealRunner** is the primary command delivery vehicle. It contains encrypted .NET assemblies (XOR with 255-byte key, optionally gzip compressed) serialized with `BinaryFormatter`. Each CerealRunner encapsulates:
- A `RequestID` (UInt64) tying request to response
- An array of payload assemblies (byte[][])
- Payload index and arguments for each payload

CerealRunner is never written to disk. ESET observed **thousands** of CerealRunner binaries, each compiled for a specific task, suggesting a robust automated build-and-packaging framework on the operator side.

**CerealSprinter** is similar but used solely for loading other components (not commands). It uses a mutex based on its `ModuleVersionId` (GUID) and performs an **AMSI bypass** by setting the `amsiInitFailed` variable to `true`. Error logs are encrypted to `FallbackLog.bin`.

### Stage 3: Passive Backdoor -- CerealNeuron

CerealNeuron is the core passive backdoor, functionally similar to Neuron (attributed to Turla by UK NCSC in 2017) but assessed to be a distinct, purpose-built family.

**Network Protocol:**

CerealNeuron uses `System.Net.HttpListener` to passively wait for incoming HTTPS requests on the compromised Exchange server. Observed URI prefixes:

- `hxxps://*:443/owa/sdds/`
- `HXXPS://*:443/AUTODISCOVER/MICROSOFT.EXCHANGE.PROXYSERVICE/`
- `HXXPS://*:443/AUTODISCOVER/INTEGRATED/API/`
- `HXXPS://*:443/AUTODISCOVER/PROXYSERVICE/`
- `HXXPS://*:443/MICROSOFT-SERVER-ACTIVESYNC/INTEGRATED/API/`

Invalid requests are redirected to legitimate Exchange error pages (e.g., `/owa/auth/errorFE.aspx`).

**Encryption scheme:**
1. Request body is base64-encoded
2. First 256 bytes: RSA-2048 decrypted using a hardcoded private key (3 distinct keys observed)
3. Decrypted bytes yield AES-256 key and IV via SHA-384 hashing
4. Remaining body: AES-encrypted command
5. Integrity verified with HMAC-SHA-256

**Configuration key:** `B38C96AE6643D2AB5C0BFE823D9C9017` (MD5 hash observed in both CerealNeuron and CerealBox binaries).

### Stage 3 (Offline Variant): CerealHermit

CerealHermit is a network-less variant of CerealNeuron that reads commands from encrypted files on disk and writes results back. It operates in active mode (2-minute polling) and passive mode (60-minute polling), switching after 5 consecutive failures. Deployed alongside CerealNeuron inside CerealSprinter binaries.

### Stage 4: Process Injection -- CerealIron

CerealIron injects .NET assemblies into non-.NET processes by:
1. Opening target process via `OpenProcess`
2. Copying bootstrapper DLL (32-bit or 64-bit) headers and sections into target memory
3. Fixing relocations and imports
4. Executing via `CreateRemoteThread` calling the bootstrapper's `DllEntryPoint`
5. Bootstrapper loads CLR, loads assembly, invokes specified method

Only 32-bit CerealIron binaries observed, targeting 32-bit processes (primarily `EdgeTransport.exe`).

### Stage 5: Email Collection -- CerealBox

CerealBox is the email harvesting module, injected into `EdgeTransport.exe` (Exchange transport service). This is a **novel technique** not previously documented for any malware family.

**Injection mechanism:**
1. Obtains current application domain of EdgeTransport process
2. Adds custom `AssemblyResolve` handler loading Exchange libraries from `%ExchangeInstallPath%\Bin\` and `%ExchangeInstallPath%\Public\`
3. Accesses `mexRuntime` object from `Microsoft.Exchange.Transport` assembly
4. Retrieves `factoryTable` dictionary of `AgentFactory` objects
5. Replaces all `RoutingAgentFactory` instances with custom factories that wrap existing handlers
6. Custom agent processes messages before passing to original handler -- no new agent registered

**Collection criteria:**
- Must contain at least one `.doc`, `.docx`, or `.pdf` attachment
- AND match at least one: sender in target list, recipient in target list, subject contains target substring, or attachment name contains target substring
- Subject to ignore lists for accounts, subjects, and attachment names
- All allow/deny lists are **hardcoded** (require recompilation to update)

Collected messages are serialized as `MimeDocument`, gzip compressed, XOR encrypted, and staged on disk. New file created when staged data exceeds 5 MB. **CerealBox automatically stops 70 days after first run.**

### Operator Command Capabilities

Commands delivered via CerealRunner to CerealNeuron include:
- **Email retrieval**: Get mailboxes/messages via EWS (Exchange Web Services) SOAP requests
- **Active Directory reconnaissance**: LDAP queries for computers, users, groups, DNS records, OUs
- **WMI queries**: Process listing, volume shadow copies, active TCP connections
- **Credential theft**: LSA Secrets extraction from registry
- **File system operations**: List, read, and delete files (often staged CerealBox dumps)
- **Volume snapshot enumeration**: `NtFsControlFile` with `FSCTL_SRV_ENUMERATE_SNAPSHOTS`

## Detection & Remediation

### Immediate Actions

1. **Audit Exchange servers** for the specific file paths listed in the IOCs section, particularly:
   - `C:\Windows\System32\wbem\ncobjapi.dll` and `wbemcomn.dll` (compare hashes against known-good)
   - Files in `C:\Windows\assembly\NativeImages_v4.0.30319_64\` with Exchange-related names not generated by `ngen.exe`
2. **Review IIS/Exchange logs** for HTTP requests matching the five CerealNeuron URI prefixes
3. **Check for anomalous thread creation** targeting `EdgeTransport.exe` from non-Exchange parent processes
4. **Scan with ESET detection signatures**: MSIL/Agent.YCC, MSIL/Agent.YCA, MSIL/Agent.YBZ, Win32/Agent.AIOQ
5. **Review transport agent configuration** for unexpected or modified routing agents (`Get-TransportAgent` in Exchange Management Shell)

### Remediation

- If compromise is confirmed, assume all email traffic and credentials on the affected Exchange server are compromised
- Rotate all credentials (especially domain accounts) accessible from the Exchange server
- Rebuild the Exchange server from known-good media rather than attempting malware removal (in-memory components and native image cache poisoning complicate cleanup)
- Review email flows for evidence of data exfiltration via CerealBox (emails with .doc/.docx/.pdf attachments to/from sensitive addresses)
- Implement network segmentation to limit lateral movement from Exchange servers
- Consider migrating to Exchange Online with Conditional Access policies

### Long-Term Hardening

- Deploy endpoint detection on Exchange servers capable of monitoring .NET assembly loading and process injection
- Monitor the .NET native image cache directory for unauthorized modifications
- Implement Application Control / AppLocker policies for the `wbem` directory
- Enable PowerShell Script Block Logging and Module Logging on Exchange servers
- Monitor for AMSI bypass attempts (`amsiInitFailed`)
